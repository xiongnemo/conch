# 版本号

格式：

```text
v{主版本}.{次版本}.{补丁}-{分支}-{提交前 12 位}[-dirty]
```

- **补丁号自己往上加**：从最近的一个 `vX.Y.Z` 标签开始，往后每多一个提交，补丁号加一。`v0.1.0` 之后的第三个提交就是 `v0.1.3-main-<提交>`。补丁号从来不用手改。
- **打了标签的提交就是那个版本**：在一个 `vX.Y.Z` 标签所在的提交上、没有未提交的改动时，版本就是 `v0.1.0` 本身，不带分支和提交。
- **还没有任何标签时**从 `v0.0.1` 算起，但这只用于本地构建，不会发布。版本线从 `v0.0.1` 这个标签开始。
- **改次版本或主版本**：在想要的提交上打一个新的 `vX.Y.0` 标签并推上去。之后的提交从它往上数。
- 分支名里文件名放不下的字符换成 `-`；有未提交的改动时加 `-dirty`。
- `conch version`（或 `conch --version`）显示版本。版本由 `scripts/version.sh` 算出来，通过 `-ldflags -X` 写进 `internal/version`，CI 和本地构建用的是同一个脚本。

## 两种标签

- `vX.Y.Z`：基准标签，手动推。它决定版本线。
- `vX.Y.Z-分支-提交`：预发布的标记，由发布流程自动创建，**永远不会**成为基准（算版本时排除带 `-` 的标签）。

其他形状的标签会被 `tag-guard` 报错。

## 发布

`.github/workflows/release.yml`：

- **main 上每个通过 CI 的提交**都发布成一个 GitHub 预发布（prerelease），例如 `v0.0.5-main-0123456789ab`，标签由流程创建。
- **推一个 `vX.Y.Z` 标签**会发布这个版本：补丁号是 0（次版本或主版本升级，例如 `v0.1.0`）的是正式发布（release），会成为 Latest；其他的（例如起点 `v0.0.1`）也是预发布。
- 正式发布前先确认这个提交在 main 上通过了 CI，再打标签：

  ```sh
  git tag v0.1.0 <提交> && git push origin v0.1.0
  ```

- 软件包里的版本：正式发布是 `0.1.0`；预发布是 `0.0.5~pre`（apk 是 `0.0.5_pre`），排在 `0.0.5` 之前。浏览器扩展的版本只用 `主.次.补丁`。
- 手动运行这个流程只构建、不发布，产物放在 Actions 的 artifacts 里。
